# AQNET 광고 성과 통합 대시보드

Naver · Meta · Google 광고 데이터를 공통 구조로 정규화하고, 기간·매체별 성과를 조회하는 API(`/api/summary`, `/api/campaigns`)와 웹 대시보드입니다.

- 문제지 06 검증값 10개 일치 (노출 38,000 · 광고비 420,000원 · ROAS 357.14% 등)
- `npm test` 27개 통과 (자체 작성 26개)
- 외부 패키지 없음 (Node.js 20 이상)

---

## 1. 실행 방법

Node.js 20 이상, 외부 패키지 설치 없음.

```bash
npm start   # http://localhost:3000  (PORT 환경변수로 포트 변경 가능)
npm test    # 전체 테스트
```

| 확인 대상 | 주소 |
| --- | --- |
| 대시보드 | http://localhost:3000 (성과 요약) · http://localhost:3000/#campaigns (캠페인 실적) |
| API | http://localhost:3000/api/summary?start=2026-11-01&end=2026-11-02&platform=naver · http://localhost:3000/api/campaigns |
| 400 응답 예시 | http://localhost:3000/api/summary?platform=kakao |

## 2. 구현 내용

> 각 파일 맨 위에 처리 흐름 요약이 있고, 본문은 번호 섹션으로 나뉘어 있습니다.
> 읽는 순서: `src/analytics.js` → `server.js` → `public/app.js` → `tests/analytics.test.mjs`

### API — `src/analytics.js`

처리 흐름: **정규화 → 쿼리 검증 → 필터 → 집계 → 정렬**

- **정규화**: 매체별 필드 매핑을 `MAPPERS` 한곳에 모아, 매체를 추가할 때 매퍼 하나만 추가하면 되도록 구성. Meta 문자열 숫자 → `number`, Google `cost_micros` → 원
- **집계**: 원본 합계를 먼저 구한 뒤 비율 계산(행별 비율의 평균 X). 분모가 0이면 `null`, 소수 둘째 자리 반올림
- **정렬**: summary는 매체명 오름차순 / campaigns는 광고비 내림차순 → 동점 시 `platform` → `campaignId`
- **오류 응답**: 잘못된 조회 조건은 `InvalidQueryError` → `400 { error: "INVALID_QUERY", message }`

### 문제지에 명시되지 않아 직접 정한 규칙

| 상황 | 처리 | 이유 |
| --- | --- | --- |
| 달력에 없는 날짜 (`2026-02-30`) | 400 | 형식만 맞고 실제로 없는 날짜도 잘못된 입력 |
| `start == end` | 허용 | "양쪽 날짜 포함"이므로 하루 조회 |
| `platform=Naver` (대문자) | 400 | 허용 값이 `naver/meta/google`로 명시되어 정확히 일치만 허용 |
| `platform=naver&platform=meta` (중복) | 400 | 단일 선택 필터라 의도가 모호한 요청을 거부 |
| `platform=` (빈 값) | 전체 조회 | 화면의 "전체" 선택 값이 빈 문자열 |
| 숫자로 바꿀 수 없는 원본 값 | 500 | `0`으로 넘기면 합계가 조용히 틀어지므로 오류로 처리 |
| 날짜별로 캠페인명이 다른 경우 | 최근 날짜의 이름 사용 | 최신 명칭이 현재 캠페인을 대표 |
| 반올림 방식 | 지수 표기 이동(`1.005e2`) | `Math.round(1.005*100)/100`이 `1`이 되는 부동소수 오차 방지 |

### 화면 — `public/` (바닐라 JS)

- **필터**: 시작일·종료일·매체 + `조회`·`초기화`. 조건은 URL에 반영되어 새로고침·뒤로가기에도 유지
- **화면**: 성과 요약(필수 지표 5개 카드, 매체별 점유율·지표) / 캠페인 실적(필수 열 + 정렬·검색·합계)
- **상태 처리**: 로딩·에러(다시 시도)·빈 결과 안내, 연속 조회 시 이전 요청 취소
- **보안·접근성**: `innerHTML` 미사용(XSS 방지), WCAG AA 대비·키보드·스크린리더 지원, 외부 라이브러리 없이 오프라인 동작

### 서버 — `server.js` (스타터코드에서 소폭 수정)

- `server`를 export하고 직접 실행할 때만 `listen` → 테스트에서 실제 HTTP 400 응답까지 검증
- 구현 완료로 필요 없어진 501(`NOT_IMPLEMENTED`) 처리 삭제

## 4. 미완성 항목 / 한계

- **데이터 규모**: 서버 시작 시 JSON을 메모리에 올리는 구조이며, 대용량 데이터·DB 연동은 고려하지 않았습니다.
- **타임존**: 원본 날짜를 그대로 사용합니다. 매체별 리포트 시간대가 다른 실제 환경에서는 보정이 필요합니다.
- **데이터 오류**: 원본에 숫자가 아닌 값이 하나라도 있으면 요청 전체가 500입니다. 실서비스라면 문제 행만 제외하고 로그를 남기는 방식이 필요합니다.
- **프론트엔드 테스트**: 화면은 스크린샷으로 확인했고, 브라우저 자동화(E2E)·실제 스크린리더 테스트는 하지 못했습니다.
- **미구현**: 캠페인 페이지네이션, 기간 프리셋(최근 7일 등), CSV 다운로드, 전기 대비 증감률(이전 기간 데이터가 없어 제외)

## 5. AI 사용 범위

사용 도구: **Claude Code (Claude Opus)**

AI는 코드 작성을, 저는 요구사항 판단·방향 결정·검증을 맡는 방식으로 작업했습니다.

| 단계 | AI | 본인 |
| --- | --- | --- |
| 요구사항 | 문제지 항목 정리, 명시되지 않은 경우의 처리 방안 제안 | 제안된 규칙(대소문자·중복 파라미터·빈 값 등)의 근거를 검토하고 확정 |
| API 구현 | `src/analytics.js` 작성 | 정규화·집계·정렬 흐름 검토, 문제지 항목별 누락 점검 |
| 화면 구현 | `public/` 코드 작성 | 화면 구성·디자인 방향 결정 및 반복 수정 요청 (사이드바·화면 분리, 정렬 방식, 가독성, 스크롤 제거 등) |
| 테스트 | `tests/analytics.test.mjs` 작성 | 테스트가 문제지 요구사항을 빠짐없이 다루는지 확인 |
| 검증 | 테스트·스크린샷 실행 | 06 검증값과 400 응답을 실제 서버에서 직접 확인 |
| 문서 | README 초안 | 내용 확인 및 정리 |

- **검증 원칙**: 화면의 모든 숫자는 API 응답에서만 나오도록 했고, 데이터에 없는 수치(전기 대비 증감률 등)는 넣지 않았습니다.
